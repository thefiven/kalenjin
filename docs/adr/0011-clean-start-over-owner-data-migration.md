# Repartir de zéro plutôt que migrer les données mono-utilisateur existantes

L'issue #25 posait la question de faire passer les données mono-utilisateur existantes (activités, objectifs, plans, rapports de l'owner) vers le nouveau modèle multi-tenant, ou de repartir d'une base vide si la migration s'avérait trop complexe (issue #31). Au moment où la migration de scoping par utilisateur (`080d4ba23719`, issue #28) a été écrite, aucune instance Kalenjin n'était déployée avec des données réelles — le projet était encore en développement, jamais lancé en production sur le k3s de l'owner. Cette migration a donc ajouté les colonnes `user_id` en `NOT NULL` directement, sans étape de backfill : un choix qui suppose des tables vides, et qui aurait échoué si des lignes préexistantes avaient été présentes.

C'est donc un repartir-de-zéro par construction, pas une décision explicite prise consciemment au moment de l'écrire — d'où cet ADR après coup, pour que ce choix ne reste pas implicite dans une migration Alembic sans contexte. Si une vraie instance avec des données de l'owner existait un jour avant un déploiement multi-tenant, cette décision serait à revoir : il faudrait alors écrire une étape de backfill (créer le `User` de l'owner, peupler `user_id` sur les lignes existantes) avant d'imposer la contrainte `NOT NULL`, plutôt que de perdre ces données.
